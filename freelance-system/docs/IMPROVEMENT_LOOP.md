# Цикл самоулучшения

Без этих четырёх механизмов система — разовый скрипт, а не обучающийся
конвейер. Каждый из них имеет конкретную реализацию в этом пакете.

## 1. Замкнутый цикл результата → память

Каждая точка подтверждения — источник данных, не просто "да/нет".
Когда ты одобряешь/правишь заявку, план или сдачу — причина правки
записывается как факт с временной меткой в Graphiti (не просто текстовый
лог, а структурированный факт: "заявка X отклонена, причина: тон слишком
формальный для клиента Y").

Реализация: `track_outcome.py` пишет в таблицу `decisions` (см. schema.sql)
и синхронизирует значимые записи в Graphiti через его API.

## 2. Разделение "что сработало" от "что просто произошло"

Отправка заявки — событие. Выигрыш тендера — исход. Между ними может
пройти неделя. Нужен отдельный трекинг через время.

Реализация: таблица `outcomes` со статусом (`pending` → `won`/`lost`/
`delivered`/`client_revision_requested`) и `track_outcome.py`,
запускаемый по cron, который сверяет статусы через API биржи там,
где это возможно, иначе — вручную помечается тобой одной командой.

## 3. Периодическая ревизия промптов на основе данных

Раз в 2-4 недели, не "на глаз":
- Deepseek прогоняет все решения за период, ищет паттерны ошибок
  (какие формулировки заявок выигрывали чаще, какие типы вакансий
  система неправильно скорила)
- Claude формулирует конкретные правки в промпты/few-shot примеры
  на основе этого анализа, но **не применяет их автоматически**

Реализация: `weekly_review.py` — генерирует отчёт с предложенными
изменениями, ты просматриваешь и одобряешь применение. Это ещё одна,
неявная четвёртая точка подтверждения — но на уровне самой системы,
а не отдельной заявки.

## 4. Явная эскалация на границе уверенности

Система отслеживает свою неуверенность, а не просто выполняет.
Если скоринг колеблется около порога (см. `confirmation_points.yaml`),
или тип вакансии/задачи нетипичен (мало похожих примеров в памяти) —
это автоматически становится дополнительной точкой подтверждения,
даже если по умолчанию для этого слоя стоит автономный режим.

Практически: единственный способ безопасно расширять автономность —
не "довериться и перестать проверять", а дать системе самой
сигнализировать о нетипичных случаях, и постепенно понижать порог
эскалации только там, где статистика (`outcomes`) показывает
стабильно хорошие результаты.
