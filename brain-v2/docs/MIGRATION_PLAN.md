# План миграции с текущей системы на v2

Принцип: не переписывать всё сразу. Тестируем на одном проекте, сравниваем,
только потом расширяем.

## Этап 0 — Подготовка (не трогаем существующее)

- [ ] Существующий Postgres/pgvector остаётся как есть, ничего не ломаем
- [ ] Поднимаем новый стек (Neo4j + Graphiti) рядом, изолированно
- [ ] Убеждаемся, что оба стека работают параллельно без конфликтов портов/ресурсов

## Этап 1 — Пилот на одном проекте

Выбираем **биддинг-агент** (уже определён как приоритет для дохода).

- [ ] Направляем только его контекст/факты в Graphiti вместо текущей логики
- [ ] Заменяем n8n-логику для этого проекта на Claude Code + MCP-инструменты
- [ ] Не трогаем остальные 3 проекта — они продолжают работать на старой схеме

## Этап 2 — Оценка (2-3 недели использования)

Сравниваем по honest-критериям:
- [ ] Быстрее ли находятся релевантные факты (subjective + при возможности замеры)
- [ ] Быстрее ли итерация через код (Claude Code) vs визуальный n8n-редактор
- [ ] Не возникло ли новых проблем (сложность поддержки, баги в Graphiti/Neo4j)
- [ ] Стоимость: не выросли ли расходы на инфраструктуру/токены неоправданно

## Этап 3 — Решение

Если тест положительный:
- [ ] Переносим контент-фабрику, Godot-проект, сайты на новую архитектуру
- [ ] Настраиваем `obsidian_export.py` на регулярный запуск (cron) для всех проектов
- [ ] Постепенно сужаем роль n8n до чистых триггеров/интеграций везде

Если тест отрицательный:
- [ ] Откатываемся к исходному Phase 1 плану (Obsidian + n8n + pgvector)
- [ ] Документируем, что именно не сработало — в `DECISIONS.md`, для истории

## Этап 4 (опционально, не раньше этапа 3) — Расширения

- [ ] vibe-kanban — для параллельных Claude Code сессий по проектам
- [ ] Letta — если понадобится агенто-управляемая архивная память
- [ ] Temporal — если понадобится надёжность длинных процессов с ретраями
